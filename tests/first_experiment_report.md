# 첫 번째 오류 분석 실험 보고서

## 실험 개요

- 대상: `fpe`, `abort`, `many`, `noout`, `segv`, `exit3` 6개 테스트
- 평가 기준: 테스트 코드의 실제 종료 원인과 LLM 설명의 원인·위치·수정 제안이 일치하는지 확인
- 종합 결과:
  - **오류 원인을 대체로 맞게 식별한 테스트: 6/6개**
  - **설명까지 큰 문제 없이 맞은 테스트: 4/6개** (`fpe`, `abort`, `many`, `noout`)
  - **중요한 설명 또는 수정 제안이 부정확했던 테스트: 2/6개** (`segv`, `exit3`)
  - `noout`은 원인 설명은 맞았지만 용어 오타가 있었음

## 테스트별 결과

### 1. `tests/fpe.c` — 정수 0 나누기

- 실제 코드
  - 4행에서 `divisor`를 0으로 설정
  - 7행의 `dividend / divisor` 실행 중 SIGFPE(8) 발생
- 분석 결과
  - 7행의 나눗셈과 4행의 분모 값 0을 지목한 설명은 정확함
  - 분모가 0인지 확인하거나 유효한 값을 보장하라는 제안도 적절함
- 판정: **맞음**

### 2. `tests/abort.c` — 같은 메모리의 중복 해제

- 실제 코드
  - 12행에서 `release(pointer)` 첫 번째 호출
  - 13행에서 같은 주소를 다시 해제하며 glibc가 SIGABRT(6) 발생
- 분석 결과
  - 두 해제 호출을 원인으로 지목한 설명은 코드와 일치함
  - 두 번째 해제를 제거하라는 제안도 적절함
- 판정: **맞음**

### 3. `tests/many.c` — 출력 후 명시적 SIGSEGV

- 실제 코드
  - 7~8행에서 15줄 출력
  - 9행에서 출력 버퍼를 비운 뒤 10행의 `raise(SIGSEGV)` 호출
- 분석 결과
  - 마지막 출력 이후 종료된 이유를 10행의 의도적 시그널 발생으로 찾음
  - 테스트가 크래시 출력 기록을 확인하는 용도라는 설명도 적절함
- 판정: **맞음**

### 4. `tests/noout.c` — 출력 없는 명시적 SIGSEGV

- 실제 코드
  - 출력 없이 6행의 `raise(SIGSEGV)` 호출
- 분석 결과
  - 메모리 접근 오류가 아니라 코드가 직접 SIGSEGV를 발생시켰다는 핵심 설명은 맞음
  - 정상 종료를 원할 때 해당 호출을 제거하라는 제안은 맞지만, 이 테스트의 목적은 시그널 재현이므로 테스트 코드에서는 호출을 유지해야 함
  - 출력에 나온 “선회널”은 오타이며 “세그멘테이션 폴트” 또는 “세그폴트”가 맞음
- 판정: **핵심 분석 맞음, 표현 개선 필요**

### 5. `tests/segv.c` — 널 포인터 역참조

- 실제 코드
  - 5행에서 `pointer`를 `NULL`로 초기화
  - 10행의 `*pointer = 1`에서 SIGSEGV(11) 발생
- 분석 결과
  - 원인과 오류 행을 찾은 것은 맞음
  - 다만 “10번 줄이 실행되지 않았다”는 의미로 읽히는 설명은 부정확함. 10행을 실행하다가 크래시가 발생함
  - “포인터 할당을 제거”하라는 제안은 잘못됨. 현재 포인터는 이미 `NULL`이며, 유효한 주소를 대입하거나 역참조 전에 널 검사를 해야 함
- 판정: **원인 식별 맞음, 실행 설명과 수정 제안 틀림**

### 6. `tests/exit3.c` — 0이 아닌 종료 코드

- 실제 코드
  - 4행의 `return 3`으로 프로세스가 시그널 없이 종료 코드 3을 반환
- 분석 결과
  - 원인 행과 시그널 종료가 아니라는 점은 맞음
  - “정상 종료”라는 표현은 프로세스가 시그널로 죽지 않았다는 의미에서는 맞지만, 종료 코드 3은 성공 코드 0이 아니므로 CrashDoc에서는 비정상 종료 코드로 기록됨
  - 테스트 자체는 종료 코드 3을 확인하기 위한 것이므로 그대로 두는 것이 맞음
- 판정: **원인 식별 맞음, 종료 상태 해석은 불명확**

## 개선할 점

- 규칙 분석 결과의 종료 유형과 충돌하는 결론을 LLM이 내리지 않도록 프롬프트를 보강
  - 종료 코드가 0이 아니면 이를 성공 종료라고 단정하지 말 것
  - 테스트 코드의 의도와 프로그램 실행 결과의 분류를 구분할 것
- 수정 제안은 실제 코드 상태를 기준으로 작성
  - 널 포인터가 이미 `NULL`인 경우 “포인터 할당 제거” 대신 유효 주소 대입 또는 널 검사 제안
  - 오류가 발생한 행은 “실행되지 않은 행”이 아니라 “실행 중 실패한 행”으로 표현
- 원인이 명시적인 `raise(SIGSEGV)`인 테스트는 의도적 재현인지 설명하고, 테스트 목적을 유지할 때는 해당 코드를 제거하라고 권하지 않도록 안내
- 응답 후처리에서 알려진 시그널·메모리 오류 용어를 점검해 오타를 줄임

## 결론

- 6개 모두 주요 오류 원인 또는 종료 방식을 찾아냈음
- `fpe`, `abort`, `many`는 원인·위치·수정 방향이 코드와 잘 맞았음
- `noout`은 핵심 분석은 맞지만 오타와 테스트 목적을 고려한 표현 개선이 필요함
- `segv`, `exit3`은 핵심 원인은 찾았지만 수정 제안 또는 종료 상태 설명에 부정확한 부분이 있음
- 다음 개선 우선순위는 **규칙 결과와 LLM 설명의 일관성**, **실제 코드에 맞는 수정 제안**, **테스트 목적과 제품 수정 권고의 구분**임
